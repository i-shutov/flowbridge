# Управляемый SSH, восстановление и границы непрерывности

Обновлено 2026-10-28 после уточнения пользователя. Встроенный watchdog устраняет необходимость запускать отдельную команду `ssh -D ...`. Он не превращает SSH в протокол восстановления уже существующих TCP-сессий.

## Реализованный путь этого выпуска

Приложение управляет нативным OpenSSH как дочерним процессом без терминала и без shell-команд. Настройки типизированы: host, SSH port, user, private key, known_hosts, локальный SOCKS port, compression, keepalive interval/count, connect/startup timeout и задержки повторного запуска. Своё имя сервера и учётную запись вводит пользователь; пароль архива-референса к SSH отношения не имеет.

Supervisor имеет состояния `stopped → starting → ready → reconnecting`, а также `failed`. Ready требует живого дочернего процесса и успешного SOCKS5 greeting на выделенном порту. Наличие процесса само по себе недостаточно. Такая проверка подтверждает локальный SOCKS endpoint, а не доступность каждого конечного интернет-сервиса. SSH ServerAlive отвечает за обнаружение зависшего канала до сервера.

При выходе процесса, истечении startup deadline или отказе greeting watchdog завершает только принадлежащий ему процесс, освобождает его ресурсы и использует ограниченный exponential backoff. Явный Stop отменяет будущие перезапуски. Занятый чужим процессом локальный порт — ошибка, а не повод завершить тот процесс. События и stderr ограничены по размеру.

На Windows применяется Job Object с kill-on-close; explicit Stop уничтожает child и на других ОС. На Unix/macOS аварийное убийство самого приложения не даёт этой реализации Windows-подобной гарантии завершения SSH child; это отражено полем `parent_exit_cleanup`. Для строгого daemon lifecycle потребуется отдельный launchd/helper этап. Нормальное закрытие GUI останавливает engine/capture и принадлежащий ему SSH.

## Как переживаются короткие сбои

Локальный вход FlowBridge остаётся на одном порту. После SOCKS-запроса **новое** соединение, которому нужен управляемый upstream, может ждать его готовности до 30 секунд. Граница настраивается в gate API до 120 секунд. Direct, Block и другие upstream не ждут этот туннель. Остановка движка немедленно отменяет ожидания. Если клиент имеет собственный более короткий timeout, он может завершить запрос раньше.

Пока upstream не готов, FlowBridge не открывает соединение назначения и не посылает прикладные байты. После восстановления выполняется одно открытие маршрута. Время ожидания ограничено; память/число клиентов ограничены capacity движка. Если срок истёк — клиент получает явную ошибку.

**Установленные TCP-соединения при полном разрыве SSH могут оборваться.** Их байты не перепосылаются через новый канал: повтор уже принятого POST, оплаты, AI generation или tool call может выполнить действие дважды. HTTP retry/resume — решение соответствующего приложения/протокола, а не универсальное свойство TCP-прокси. Удержать локальный socket открытым недостаточно, если удалённый socket и состояние SSH channel уже потеряны.

Реализованный gate относится к общему local SOCKS Engine. Отдельные системные provider/service процессы пока не разделяют его состояние; native retry/grace нельзя объявлять проверенным по работе local режима.

## Аутентификация и понятная конфигурация

Используются ключ или уже настроенный SSH agent. `BatchMode=yes` не допускает незаметно зависшего password/confirmation prompt; `StrictHostKeyChecking=yes` не подменяется accept-any. При неизвестном/изменившемся ключе сервера приложение сообщает причину и необходимость проверить fingerprint по доверенному каналу. Можно выбрать существующий known_hosts. Первый trust-enrollment wizard и встроенный password/Keychain/Credential Manager ещё требуют отдельного завершения.

`-F none` предотвращает неожиданные команды/forwarding из произвольного SSH config; приложение передаёт разрешённые параметры явно. `-N -T` исключают remote command и TTY, agent/X11 forwarding выключены. Пути передаются argv, а known_hosts дополнительно экранируется для грамматики OpenSSH; shell не используется. OpenSSH client должен быть установлен: Windows Optional Feature/OpenSSH Client или штатный `/usr/bin/ssh` macOS. Если его нет, GUI показывает ошибку, а не сообщает Connected.

## Режим с сохранением TCP при смене канала — следующий протокол

Для более сильной гарантии нужен **постоянный relay на сервере**, независимый от жизни конкретного SSH-сеанса. Следующая архитектура предусматривает:

1. Локальный agent сохраняет client TCP sockets; remote relay сохраняет открытые sockets назначения в пределах reconnect grace.
2. Между ними идёт возобновляемый multiplexed transport. SSH остаётся шифрованным аутентифицированным carrier, а не единственным владельцем сессий.
3. Каждый поток имеет непереиспользуемый ID, отдельные 64-bit byte offsets двух направлений и ACK. Новый carrier предъявляет session token и epoch; старый carrier после смены epoch перестаёт иметь право отправлять данные.
4. DATA frames дедуплицируются по offset; подтверждённые байты не записываются в target повторно. OPEN тоже имеет idempotency key, чтобы reconnect не создавал второй target socket. FIN/RESET являются упорядоченными управляющими событиями.
5. Bounded replay buffers и flow-control окна создают backpressure на клиенте, а не бесконечный рост RAM. Переполнение или истечение grace дают определённый terminal error.
6. Token принадлежит аутентифицированному пользователю/инстансу; он не логируется и не передаётся в командной строке. Relay доступен через защищённый carrier/локальный server socket, без обязательного публичного listening port.

Это сохраняет TCP только пока живы оба agent, retained state и сам target socket, а сервер назначения не завершил соединение по своему timeout. Reboot relay, потеря state, слишком длинный разрыв и истечение лимитов остаются terminal. Гарантия «никогда не заметят любой сбой» технически недостижима.

Этот protocol/remote agent **не реализован в поставляемом бинарнике**. До реализации нужны fault-injection тесты: обрывы до/после ACK, дубли кадров, смена epoch, half-close, reorder и buffer exhaustion. Deployment требует доступа к серверу и выбранной модели его эксплуатации. Watchdog текущего выпуска не называется resumable relay.

## Шаблоны AI / Web

`resources/presets.json` содержит каталог discovery hints и пресеты AI, Web, AI + Web. Подсказка имени не доказывает установку или издателя: native discovery проверяет реальные локальные paths/metadata. Результат остаётся видимым пользователю, приложения можно включать/исключать и добавлять вручную.

Для системного режима выбранные приложения направляются в туннель, остальные по умолчанию Direct. Блокировка остальных — отдельный явный выбор. Windows текущего WFP source использует captured executable basename, Mac — наблюдаемый signing/bundle identifier; профили платформ не считаются автоматически взаимозаменяемыми. Helper processes и приложения внутри browser tab могут требовать дополнительных правил.

В local SOCKS режиме FlowBridge не видит удостоверенный исходный процесс: шаблоны приложений не создают фиктивного системного захвата. Этот режим обслуживает клиентов, явно настроенных на SOCKS; native selections предназначены для системного профиля после готовности backend. AI-сайт в браузере идентифицируется как браузер; отличить его от других вкладок одним правилом по процессу нельзя.
