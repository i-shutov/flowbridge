# FlowBridge — действующий план выпуска

**Обновлено: 27 ноября 2026, МСК.** Ближайший результат — проверенный внутренний
`0.3.0-beta.3` с явным SOCKS5 и управляемым SSH. Выпуск `1.0` с прозрачным
перехватом остаётся отдельным этапом. [Машинный реестр выполнения](qa/release-1.0/RELEASE_EXECUTION_20261127.json).

Этот документ заменяет накопленные сводки. Они сохранены в
[истории плана до 17 ноября](RELEASE_1_0_PLAN_HISTORY_20261117.md).
Старые PASS относятся только к указанным там байтам и платформам.

## 1. Что изменилось 27 ноября

Владелец предоставил новую машину Windows 11 с runner и Codex и поручил
продолжить выполнение плана. Используем её для сборки и инженерной QA.
Runner проверен реальным заданием: `win11-flowbridge`, `VM-326272`, Windows 11
Pro build 22631, native x64 и закреплённая административная учётная запись.
Это подтверждает среду исполнения; продуктовая приёмка остаётся отдельной.

**Уточнение владельца 27 ноября: Win10 не трогать.** R7 отложен по этому
указанию; передача комплекта и любые операции на Win10 исключены из текущих
работ. Продолжаем разбор raw512, G2 и нестабильности CI. Для сборки и текущих
диагностических заданий достаточно Win11 runner; локальный Codex не требуется.

| Назначение | Действующий объём |

### R1: проверка новой машины

**Выполнено.** Браузерный вход в GitHub подтверждён, runner был `Idle` и принял
ручное задание на `main`. [Первый запуск](https://github.com/i-shutov/flowbridge/actions/runs/45981565644)
не дошёл до проверок: PowerShell отклонил загрузку временного `.ps1` при
`Restricted`. Workflow теперь передаёт команды системному PowerShell через
`cmd` и `-Command`; политика не изменяется. [Повторный запуск](https://github.com/i-shutov/flowbridge/actions/runs/45982267687)
подтвердил Windows 11 Pro build 22631, native x64, точный host/account,
административный token и `RUNNER_SMOKE_PASS`; `Restricted` сохранилась.

В service PATH найдены `ssh.exe` и `python.exe`; не найдены Git, Rust/Cargo,
CMake, MSVC/MSBuild и NSIS. Сам факт нахождения Python ещё не проверяет его
версию и исключение Store alias. [Native preflight #45984099025](https://github.com/i-shutov/flowbridge/actions/runs/45984099025)
нашёл Git, CMake, MSVC x64 и Windows SDK в обычных каталогах установки.
В первой попытке Python 3.13+ и Rust/Cargo не найдены; сборка остановилась до
создания кандидата с `PYTHON_3_13_OR_LATER_REQUIRED`. В R5 эти зависимости
подготовлены из официальных пакетов в отдельном локальном каталоге; пробная
компиляция с MSVC/SDK и полный beta.3 build завершились успешно.

В `main` добавлен [ручной native build workflow](https://github.com/i-shutov/flowbridge/actions/workflows/win11-private-beta3-build.yml),
первый commit `ee218fcffe9c7d2d69821824ea693698bc382098`, успешная версия
`7d6597eb738d16839ff7a969c5ff6644194df975`. Он использует закреплённые QA
и product SHA, сохраняет результат вне Actions workspace в новом каталоге
с отдельными ACL и не выгружает пакет. Предварительный поиск инструментов
не является доказательством компиляции сам по себе; фактические результаты R5/R6
приведены ниже.

Smoke workflow не делает checkout и не запускает код PR. Отдельная сборка
получает закреплённые product/QA SHA. Smoke доказывает работу
службы и окружения. Подготовленная ранее интерактивная GUI-приёмка отложена
вместе с R7. Успех службы в Session 0 не является GUI-приёмкой.

GitHub-коннектор не предоставляет dispatch/list-runners/delete-artifact;
для этих операций используется авторизованный браузер. Административный runner
получает только вручную запущенный workflow с проверками точного repo и `main`.

### R2: устранение несогласованной публикации CI

После merge #90 автоматически запустился прежний `main` CI и успел выгрузить
артефакты, включая `FlowBridge-windows-x64` и исходный архив. Это не beta.3
и не принятый релиз, но выгрузка противоречит внутреннему режиму.
Запуск [#45975037904](https://github.com/i-shutov/flowbridge/actions/runs/45975037904)
отменён последующим исправлением; API перечислял 11 артефактов. После нового
подтверждения владельца в момент удаления **все 11 удалены**. Каждый диалог
сверен с согласованным именем, API вернул пустой список. Сам запуск остаётся
на исходном commit `40f8b66`; оригинальный журнал Windows application доступен.
Другие артефакты не затронуты. [Точный перечень и проверка очистки](qa/release-1.0/evidence/20261127/artifact-cleanup.json).

Предыдущая автоматическая проверка требовала отдельного подтверждения в момент
операции. Владелец его предоставил; блокировка закрыта обычным подтверждением
удаления. История первоначальной выгрузки и отказа проверки сохранена в реестре.

Новый `main` CI разрешает upload только при
`github.event.repository.private == true`. В продуктовой ветке такая защита
внесена во все 29 upload-шагов. Сборки и тесты продолжают выполняться.
Количество новых артефактов проверять отдельно от результата тестов.

На проверенных current source/QA запусках API подтвердил 0 артефактов после
завершения. Точные результаты и ссылки сохранены в
[CI observation](qa/release-1.0/evidence/20261127/ci-observation.json).
Source Rust/native прошёл 5/5 после повторного запуска только Windows job
на прежнем дереве: первый `WinError 10013` в paired DNS test не повторился.
Причина первого сбоя не установлена. Managed SSH прошёл; отдельная raw-проба
потеряла соединение на 244 каналах. В серверном журнале есть
`pipe(notify_pipe) failed Too many open files [postauth]`; связь этого отказа
с ресурсом Windows OpenSSH подтверждена, универсальный предел SSH не установлен.
Hosted G2 остановился с `kernel_connection_id_missing`.
Эти два отказа не преобразуются в PASS на основании успешного staging.

Финальный [Real Windows OpenSSH run на QA c671bc1](https://github.com/i-shutov/flowbridge/actions/runs/45988927279)

и четыре процесса прошли; raw достиг 244 и не подтвердил восстановление.
Остальные пять workflow этого QA head прошли; у всех шести 0 артефактов.
Это наследуемый QA source, а не замена проверки закреплённого product `44f1fc0`.

Нестабильность macOS локализована в тестовом резервировании loopback-порта:
между пробным bind/release и preflight возникал `EADDRINUSE` до запуска дочернего
процесса. В QA commit `295fd7051646c1d9907904edc2ea0a1d01ceb671` два оставшихся
теста используют существующий ограниченный повтор только этого состояния.
Таймаут Stop 750 мс и проверки поведения сохранены; production-код не меняется.
[Новый Rust/native CI](https://github.com/i-shutov/flowbridge/actions/runs/45997867096)
прошёл 5/5 с первой попытки, артефактов 0. Оба проблемных теста прошли на macOS;

Диагностические изменения вынесены в отдельный [PR #93](https://github.com/i-shutov/flowbridge/pull/93),

Raw-проба не загружает FlowBridge FFI; при отказе сохраняются безопасные счётчики.
Это исправления тестов и диагностики; готовый beta.3 candidate не изменён.

В [новом строгом raw run](https://github.com/i-shutov/flowbridge/actions/runs/45998507203/job/140503871736)

В этом конкретном прогоне ресурсного маркера нет — прежний серверный EMFILE
не приписывается новому запуску. [Разбор](qa/release-1.0/evidence/20261127/raw512-investigation.json).

[Проверка ETW на Win11](https://github.com/i-shutov/flowbridge/actions/runs/45998584523)
выполнилась на `VM-326272`: все четыре тестовых подключения попали в трассу,
но два IPv4 и два IPv6 имеют нулевой `connid`. Результат — FAIL
`kernel_connection_id_missing`, `G2_PACKET_BOUND=UNPROVED`. Очистка собственной
сессии/процессов и приватной трассы подтверждена, артефактов 0. Таким образом,
нулевые ID наблюдаются и на hosted Windows, и на нативной Win11; источник нуля
в provider/decoder этим опытом не установлен.
[Оригинальная безопасная сводка](qa/release-1.0/evidence/20261127/native-win11-g2.json).

Дополнительная [проба собственного ALE endpoint на Win11](https://github.com/i-shutov/flowbridge/actions/runs/45999914730)
прошла. На двух одновременно открытых собственных IPv4 loopback-соединениях
`SIO_QUERY_WFP_ALE_ENDPOINT_HANDLE` вернул ровно восемь байт, ненулевые,
стабильные при повторном запросе и различные между сокетами значения.
Стороны каждой пары проверены до IOCTL; четыре запроса выполнены, сокеты
закрыты, приватный временный каталог удалён, артефактов 0. Исходник
`94b13b0c0ae4bc75c799903e44d55e81a45e10d9`, локальные тесты 6/6.
[Сводка и точные пины](qa/release-1.0/evidence/20261127/native-win11-ale-endpoint.json).

Это подтверждает доступность документированного API собственного сокета.
Endpoint handle не отождествляется с ETW `connid` и не связывает исходный
процесс с перенаправленным трафиком. Флаги G2, packet ownership и origin process
остаются false. Код отдельного WSK-прототипа уже скомпилирован; результаты и
ограничения приведены в разделе 5. Для нативной проверки того же принятого
socket object, redirect records, origin epoch, policy generation и одноразового
CLAIM нужен отдельно проверенный подписанный kernel-стенд. Установка/загрузка
драйвера в этой работе не выполнялась.

Итог завершённых проверок: QA source `295fd705` и последующий документный head
`ec0a8ebb` — по 13/13 jobs в шести workflow, с первой попытки и без артефактов.
[Проверка ec0a8ebb](qa/release-1.0/evidence/20261127/qa-ec0-terminal-ci.json)

восстановлений; его PASS не закрывает новый строгий порог 512.
[Финальная сводка CI и нативных наблюдений](qa/release-1.0/evidence/20261127/release-limit-ci.json).

### R4–R6: воспроизводимая приватная сборка

Использовать два checkout: закреплённый продуктовый source и QA-инструмент.
[`stage_internal_beta3.py`](../tools/stage_internal_beta3.py) проверяет source SHA,
чистоту, девять версионных файлов, семь пакетов workspace в Cargo.lock,
пустой список remotes и неприсвоенные release flags.
[Команды и входные данные](qa/release-1.0/checkpoints/WIN11_BETA3_BUILD_RUNBOOK_20261127.md).

Исправления 27 ноября:

- Отрицательный тест версии подставляет неверную версию и после перехода на `.3`.
- Индекс Git строится из точных blobs без фильтров с сохранением executable mode:
  четыре исторических CRLF-файла больше не переписываются молча.
- Полное дерево проверяется по path/mode/blob; пакетные тесты запускаются
  на действительно подготовленном beta.3 source.
- Для локальной сборки обязательны официальный NSIS 3.13 ZIP с закреплённым
  SHA-256 и Windows client x64. NSIS извлекается отдельно, глобальный PATH не
  меняется. Windows Server не засчитывается как client acceptance.

**Нативная сборка завершена 27 ноября, 14:01 МСК.** [Запуск на Win11](https://github.com/i-shutov/flowbridge/actions/runs/45986630920)
прошёл; GitHub Actions artifacts — 0. Python 3.13.17, Rust 1.100.0 и официальный
NSIS 3.13 проверены перед использованием; использованы установленные MSVC/SDK/CMake.
Первая попытка подготовки инструментов выявила неподдерживаемый `curl --compressed`

- Standalone beta.3 commit: `c6ead0f31de4c118453913d733f537ba421af616`.
- Tree: `19df7a94071f38be6b8aa3530e1ded7a954a02a8`, совпадает с проверенным staging.

- Исходный manifest, GUI/CLI/FFI и все 13 файлов payload повторно проверены;

## 5. Следующий этап: полноценный Windows 1.0

Нужны signed native WFP/ALE и доказанная связь выбранного процесса с сокетом,
policy generation, исходным назначением и решением маршрутизации. Затем —
IPv4/IPv6 TCP, no-DIRECT при отказах, DNS/UDP/QUIC политика, восстановление,
ресурсная QA, signed RC и независимая приёмка.
[WIN-00…09](qa/release-1.0/WINDOWS_FIRST_GATES_20261115.json)
сохраняет `windows_1_0_accepted=false`.

Raw512 и G2 ведутся как отдельные технические ограничения. В проверенном
[Win32 OpenSSH v10.4.0.0](https://github.com/PowerShell/openssh-portable/blob/v10.4.0.0/contrib/win32/win32compat/inc/sys/select.h)
`MAX_FDS` равен 256; [аллокатор таблицы](https://github.com/PowerShell/openssh-portable/blob/v10.4.0.0/contrib/win32/win32compat/w32fd.c)
возвращает `EMFILE` при исчерпании. Это таблица совместимости внутри процесса,
не общий лимит Windows HANDLE. Серверный EMFILE согласуется с этим механизмом;
точную сборку inbox-клиента ещё нельзя атрибутировать только по его версии.
Для 512 каналов одного backend нужны проверенные клиент и сервер с достаточной
ёмкостью и новый строгий прогон. Рабочий managed pool остаётся отдельным результатом.

Подготовлен отдельный сценарий сборки лабораторных клиента и сервера из официального source
`274893f8`: единственное изменение upstream — `MAX_FDS` 256 → 1024. Все версии
vcpkg/зависимостей закреплены; подписанный runtime продукта и frozen beta.3
не меняются. Лаборатория выполняется на временном hosted Windows Server 2022.
Первый запуск остановился на подготовке vcpkg без достаточной диагностики.
Второй установил конкретный отказ: частичный Git clone не смог догрузить blobs
для исторических портов через `checkout-index`. Исправление загружает всю историю
того же закреплённого vcpkg SHA; нужные деревья проверены извлечением без origin.
Повторный [запуск с исправлением](https://github.com/i-shutov/flowbridge/actions/runs/46007206276)
проверяет сборку, затем строгие 512 удерживаемых соединений и 16 восстановлений.
До завершения это `IN_PROGRESS`; первые два запуска не измерили ёмкость.
[История попыток и исправление](qa/release-1.0/evidence/20261127/raw512-source-lab.json).
Даже успешный опыт с неподписанными лабораторными бинарниками потребует отдельного
решения о production runtime; изолированная причинность MAX_FDS требует парного A/B.

G2 требует достоверного kernel connection ID и последующей связи с пакетами
и политикой WFP/ALE. Диагностика на Win11 должна различать отсутствующее поле,
нулевой ID и неполное наблюдение; совпадение адресов или имени процесса не
подменяет эту связь. Проверка loopback ETW без драйвера сама по себе не закрывает
`G2_PACKET_BOUND` и не разрешает `1.0`.

### G2: прототип принятого WSK socket object

Подготовлен отдельный tests-only source
`229e37263b5927167795eb2f76097299e4b9770a` на проверенной исследовательской базе
`f1ac3b04`. Код вызывает `WskAccept` для принятого `PWSK_SOCKET`, затем
запрашивает redirect context/records у того же объекта и проверяет kernel-owned
epoch, policy generation и одноразовый claim. Числовой пользовательский socket
не превращается в kernel object. Production driver и frozen beta.3 не меняются.

[Hosted WDK compile](https://github.com/i-shutov/flowbridge/actions/runs/46003874189)
прошёл с `/W4 /WX`: 0 предупреждений, 0 ошибок; SDK/WDK 10.0.28000.2526.
Девять C++ проверок authority прошли, восемь структурных мутаций отклонены.
Выполнена только компиляция kernel object: без линковки, подписи, загрузки драйвера
или нативного redirect-трафика. [Evidence](qa/release-1.0/evidence/20261127/wsk-accepted-socket-compile.json).

Следующий барьер — проверенный подписанный стенд для настоящего redirected socket,
защиты от переноса claim на другой объект, связи с пакетами и жизненного цикла.
В прототипе после отмены IRP ожидается его окончательное завершение; это ожидание
и закрытие сокета пока не имеют доказанной верхней границы. G2, packet ownership
и origin process binding остаются непринятыми.
