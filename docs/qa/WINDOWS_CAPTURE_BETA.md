# Internal beta vertical: native Windows capture

This checkpoint contains two distinct deliverables:

1. **WFP process selection and functional redirect fixture.** The kernel driver is built separately. Existing BFE QA confirms exact image selection, IPv4/IPv6 TCP policy scope and dynamic-filter cleanup without loading a driver. New `tests/windows_wfp_redirect_runtime.py` performs *real* ALE_CONNECT_REDIRECT testing when and only when a signed/test-signed WFP driver has already been installed and loaded on a dedicated, administrator-authorized Windows VM. It verifies selected native EXE -> WFP -> FlowBridgeCapture -> local test SOCKS5 -> local echo, same-basename unselected exclusion, denial without DIRECT fallback, cleanup after Stop, and independent cleanup following forced termination of a disposable GUI-owner test process. Both lifetime paths require the real driver on the authorized VM. It uses only loopback; it is **not a standalone SSH end-to-end or remote DNS test**. The dedicated VM workflow is manual and never runs on general shared GitHub runners.
2. **GUI/elevated helper integration.** FlowBridge now packages `FlowBridgeCapture.exe` beside its existing GUI/CLI, includes a read-only `--preflight`, and exposes native Start/Stop in the Applications page. The GUI writes a checked native rules profile, requests UAC explicitly and passes only full EXE paths. A unique session stop event and GUI owner PID prevent the elevated helper remaining behind after normal/abnormal GUI exit. A deliberately absent kernel driver is reported as an error; **the ordinary NSIS installer does not install or trust any driver**. Exported rules and engine Start/Stop remain separate from native system capture.

### Real dual-stack WFP VM acceptance

The prepared VM-only scripts now cover IPv4/IPv6 ALE redirect, TCP-only/UDP bypass, same-basename full-path selection, and failure/cleanup. The second script additionally exercises an actual WFP → elevated helper → GUI-owner Rust listener → mock remote-SOCKS route with SSH readiness failure/recovery and listener-loss cleanup. **None of these changes prove a real driver has been tested until the dedicated VM produces signed-off evidence.** The GUI-owner stand-in runs under the VM admin token and is not a medium-integrity GUI acceptance test. See [WFP_REAL_VM_ACCEPTANCE.md](WFP_REAL_VM_ACCEPTANCE.md) for exact gates and evidence paths.

### Running on a dedicated Windows VM

* Use an isolated Windows 10/11 or Server test VM with a snapshot, an authorized admin account, and a driver build signed/allowed under that VM's existing code-integrity policy. No guidance here requests disabling Secure Boot or production code-integrity protections.
* Install/load only the FlowBridge WFP driver using the VM operator's usual signed-driver process. Verify `FlowBridgeCapture.exe --preflight` reports `kernel_driver_accessible: true` under the test token.
* Build Rust FFI + native helper and `FlowBridgeWfpScopeQA.exe`; place `flowbridge_ffi.dll` beside the helper. Then run `FLOWBRIDGE_WFP_VM=1 python tests/windows_wfp_redirect_runtime.py --helper <absolute-helper> --probe <absolute-test-exe> --output <report.json>` from an elevated terminal. The optional GitHub Actions job uses the self-hosted `flowbridge-wfp-vm` runner label.
* Save reports and reproduce both stop and forced GUI termination. Inspect WFP filters after exit. Revert the VM snapshot on failure rather than testing on a daily-use machine.

### Boundaries and follow-up gates

* A green ordinary GitHub CI run proves *build/install/GUI preflight/explicit SOCKS*; it **does not prove kernel driver loading, real TCP redirect, unselected QUIC restrictions, remote DNS interception, or macOS extension activation**. This boundary is present in the CLI preflight and package manifest.
* **GUI-originated managed SSH capture now remains unelevated:** the normal FlowBridge GUI/engine owns the SSH supervisor, identity file and known_hosts. The selected-app WFP helper gets only a checked isolated loopback SOCKS profile and observed executable bypass paths. It rejects `--ssh-profile` when `--gui-owner` is present; Stop/window-close withdraws WFP capture before tearing down SSH. Native capture requires pressing Connect and obtaining a real ready SSH state first. This prevents GUI-originated SSH from running with the elevated helper token, but is **not** a general security audit of the elevated service/driver or file/IPC trust boundaries. Standalone administrator-controlled console/SCM mode may still own its SSH process and remains a separate review item.
* **UAC file-integrity gate:** the unelevated GUI computes SHA-256 over the exact validated native capture JSON and passes its 64-digit digest to the elevated helper. The helper re-reads the bounded file and compares the digest before opening the WFP driver. Mismatched/missing/malformed digests fail closed. The standalone developer/SCM service entry point remains separately authorized; this is not an HMAC and does not authenticate the GUI user or fix malicious pre-validation profiles. The ordinary Windows installer test verifies a modified digest is rejected before WFP activation.
* Windows system DNS NRPT activation is a separate process-level issue; a DNS-over-SSH unit test cannot prove OS DNS leakage prevention.
* Existing TCP connections cannot survive a full SSH disconnect without a protocol-preserving server-side relay.
