# FlowBridge Windows 1.0 — WIN-01 / R198 AUTH_CONNECT checkpoint

**15 ноября 2026.** Продуктовый [Draft PR #70](https://github.com/i-shutov/flowbridge/pull/70),
точный source HEAD `162e1ee164da4445f53e5c0e42a6125191b837ba`,
стек поверх WFP v3 [PR #69](https://github.com/i-shutov/flowbridge/pull/69).
Владелец разрешил разработку и испытания WFP/ALE; это **не** разрешение
на установку неподписанного драйвера или отключение SecureBoot/CI на рабочих машинах.

**Итог:** реальный продуктовый C/WFP/Win32-код собран, нативные тесты и
исходные отрицательные проверки завершились PASS. Физический G2 и выпуск 1.0 — **NO-GO**.

## P0, который сдвинут

По документации Microsoft, у физического исходящего TCP-сокета
прокси с WFP redirect records `ALE_ORIGINAL_APP_ID` может оставаться
идентификатором выбранного исходного приложения, тогда как текущий
`ALE_APP_ID` соответствует отправителю сокета. Подбор AUTH-фильтра
по `ALE_ORIGINAL_APP_ID` способен самоблокировать транспортный SSH.
Безусловное исключение по PID брокера также неприемлемо: оно создавало бы
потенциальную лазейку для выбранного DIRECT.

В новом коде выбран **отдельный AUTH-контракт**:

1. `native/windows/wfp/capture.cpp` устанавливает внутри одной динамической
   BFE-транзакции два terminating `ALE_AUTH_CONNECT` callout и фильтры
   только по **текущему OS ALE_APP_ID** выбранного EXE + TCP, для IPv4 и IPv6.
   `ALE_ORIGINAL_APP_ID` **не** используется как селектор физического SSH.
   Канонические WFP AppId выбранного и bypass EXE сверяются **до открытия
   драйвера**. Их совпадение запрещено.
2. `native/windows/wfp/driver/driver.c` создаёт kernel-only AUTH-запись
   из процессного callback PID+creation epoch+start key, настоящего WFP
   endpoint handle, исходного адреса/порта и целевого PID брокера.
   Начальный AUTH может однократно использовать её только с совпадающими
   OS-метаданными redirected-loopback. Внешний физический SSH-адрес
   не может потребить запись исходного соединения.
3. `native/windows/wfp/auth_receipt.h`: 512 невытесняемых записей.
   Повторная авторизация, повторное потребление, ошибочная инкарнация PID,
   отсутствующий endpoint, другая семья IP, неправильный порт, неверный
   callback выхода процесса или переполнение дают отказ. **Это временное
   ограничение безопасности, не готовое решение 10k потоков.**
4. Для AUTH с отсутствующим `FWPS_RIGHT_ACTION_WRITE` разрешено только
   вето ранее выставленному `PERMIT`, а не повышение чужого BLOCK.
   Microsoft WFP-значения `FWP_UINT16/UINT32` анализируются в host-order.
5. `FwpsApplyModifiedLayerData0` не имеет `NTSTATUS` результата (`void`).
   Последний код больше не выдумывает статус успешного Apply: AUTH-права
   зависят исключительно от последующих метаданных ОС. Без новой
   AUTH-классификации первоначальная запись сама ничего не разрешает.

## Какие пробелы остаются настоящими блокерами релиза

- **WIN-01/G2:** реальная работа подписанного kernel notifier,
  `ALE_CONNECT_REDIRECT` и `ALE_AUTH_CONNECT` на Windows 10/11 с
  независимым наблюдением PID/epoch/AppId/endpoint и процессов.
- **Accepted socket CLAIM:** текущая AUTH-запись — это источник
  доказательства для первоначального loopback-redirect; **не**
  реализован терминальный однократный CLAIM на *конкретном принятом
  сокете*. Требуется совместить kernel ticket с реальными context/records.
- **R198 физический outbound SSH:** необходимо на настоящем WFP стенде
  измерить обе пары `ALE_APP_ID` и `ALE_ORIGINAL_APP_ID` для исходного
  сокета и внешнего SSH, включая IPv4/v6 и reauthorization. Источниковое
  решение по CURRENT AppId ещё не доказало физическое отсутствие самоблокировки.
- **R174/R180/R181/R190:** reauthorization пока блокируется, 512
  записей без безопасной рекламации исчерпываются, конкурирующие
  sublayers/hard PERMIT, BFE dynamic session loss и STOP/crash не приняты.
- **WIN-02/03/04:** реальный выбранный IPv4/v6 TCP→Rust→управляемый SSH
  плюс независимый no-DIRECT pcap, DNS/UDP/QUIC/DoH и отсутствие
  fallback на физической Windows 10 Pro / Windows 11 Pro ещё не проверены.
- **WIN-07/09:** подпись драйвера/издателя и юридический аудит,
  отдельные тестовые VM со снимками, VNC/SYSTEM rescue/rollback,
  исходные артефакты и независимое решение GO ещё открыты.

Существующий Windows-first продукт по-прежнему **не объявляет**
`PacketBound`, физический `no-DIRECT`, `G2 PASS` или релиз 1.0.
Сохранены отдельные кроссплатформенные Rust/FFI контракты, macOS
не входит в первый релиз и не удаляется из продукта.
